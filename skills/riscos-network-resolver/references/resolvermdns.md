# ResolverMDNS reference

Use this reference only when the task is about the multicast-DNS resolver
module rather than the normal unicast `Resolver` module.

Typical triggers:

* `ResolverMDNS`
* Bonjour
* Rendezvous
* multicast DNS or mDNS
* DNS-SD / service discovery
* SWIs such as `ResolverMDNS_GetHost`, `ResolverMDNS_BrowseStart`, or
  `ResolverMDNS_RegisterService`

## Read order

Start with the generated PRM-in-XML interface document if it exists in the
tree:

* `prminxml/resolvermdns.xml`

Then confirm the exported interface and behaviour from the source:

* `cmhg/modhead` and `h/modhead` for SWI numbers, the error base, and
  handled service calls
* `h/ResolverMDNS` for returned data structures and flag definitions
* `c/veneer` for the actual SWI register contracts
* `c/query`, `c/querysrv`, `c/browse`, `c/domain`, `c/multihostent`,
  and `c/txt` for query lifecycle, returned buffers, browse sequencing,
  and TXT encoding behaviour
* `Tests/` for simple client examples; detokenise the BASIC files with
  `riscos-basicdetokenise -i Tests/<name>,ffb`

## Public interfaces

The module exports these SWIs:

* `ResolverMDNS_DCI4Statistics`
* `ResolverMDNS_RegisterService`
* `ResolverMDNS_DeregisterService`
* `ResolverMDNS_Resolve`
* `ResolverMDNS_GetHost`
* `ResolverMDNS_BrowseStart`
* `ResolverMDNS_BrowseRead`
* `ResolverMDNS_BrowseStop`
* `ResolverMDNS_GetDomains`
* `ResolverMDNS_ConvertTXT`

The SWI chunk base is `&57DC0`. The error base is `&81CBC0`.

## Core usage model

ResolverMDNS is asynchronous.

* `ResolverMDNS_Resolve`, `ResolverMDNS_GetHost`, and
  `ResolverMDNS_GetDomains` return `EINPROGRESS` in `R0` while data is still
  being collected.
* Clients either poll by repeating the same call or monitor the
  `Event_Internet` notifications generated by the module.
* Browse operations are separate: start with `BrowseStart`, inspect with
  `BrowseRead`, and release with `BrowseStop`.

Treat returned pointers as transient. The public header says returned
structures remain valid for 15 minutes, but callers should still copy out
data they need to retain.

## Important data returned

From `h/ResolverMDNS`:

* `hostent_t` for host-name and reverse-address lookups
* `hostportent_t` for service-instance resolution, including host, port, and
  one TXT block
* `browseservent_t` for browse results
* `browsedomainent_t` for domain browsing
* `resourcerecord_t` for generic resource-record queries

When documenting or reviewing callers, be clear that `ResolverMDNS_GetHost`
returns different structures depending on the low bits of the flags.

## TXT encoding rules

These encodings are shared across registration, service resolution, and TXT
conversion:

* literal: wire-format TXT data
* escaped: 0-terminated string using `&01` as the escape/separator byte
* decomposed: `txtkey_t` key/value/length triples terminated by a NULL key

`ResolverMDNS_ConvertTXT` is the conversion helper. When the destination
buffer is too small it returns the required size as a negative value in `R4`.

## Behaviour that matters

* `ResolverMDNS_GetHost` supports three lookup classes in the low three bits:
  by name, by address, and by service.
* Service lookups use the TXT encoding bits in `R0`.
* `ResolverMDNS_BrowseStart` and `ResolverMDNS_BrowseStop` reference-count
  identical browse requests.
* Passing `NULL` as the browse service means "browse service types", which
  is implemented as `_services._dns-sd._udp`.
* Passing `NULL` as a browse or registration domain means `local.`.
* `ResolverMDNS_GetDomains` prepends `local.` for the browse-domain and
  registration-domain list operations.
* `ResolverMDNS_Resolve` is a generic RR interface; for most client work,
  `ResolverMDNS_GetHost` is the more useful API.

## Events and services

The module handles these service calls:

* `Service_DCIProtocolStatus`
* `Service_DCIDriverStatus`
* `Service_InternetStatus`
* `Service_InternetVars`
* `Service_StatisticEnumerate`

It also generates `Event_Internet` subreasons for browse updates, service
resolution completion, and generic query updates. If event-driven behaviour
matters, read `prminxml/resolvermdns.xml` or `c/query`, `c/querysrv`, and
`c/browse` before making assumptions.

## Recommended output style

When answering with this reference:

* distinguish clearly between the normal `Resolver` module and `ResolverMDNS`
* prefer the generated PRM and the source over old prose in `docs/!ReadMe`
* call out which SWI register contracts are source-derived from `c/veneer`
* mention when a behaviour is asynchronous or event-driven rather than
  returning final data immediately
